
## 一、模块依赖分析 
### 1.1 直接依赖（强耦合） **PaymentService（支付引擎服务）** - 依赖位置：`src/payment/services/payment.service.ts` - 依赖方法： - `deductFromClinicAccount()` - 诊所账户扣款（Lines 559-740） - `refundToClinicAccount()` - 退款到诊所账户（Lines 741-834） - `processClinicAccountRefund()` - 处理诊所账户退款（Lines 1001-1089） - `getClinicAccountBalance()` - 获取账户余额（Lines 835-858） - 影响程度：**极高** - 需要完全重构这些方法 
### 1.2 间接依赖 - **OrderService**：仅验证诊所存在性，不直接依赖账户功能 - **OrchestrationService**：监听支付事件，但不直接调用诊所账户 
### 1.3 数据模型影响 - `clinic_accounts` 表 - 将失效 - `account_transactions` 表 - 将失效 - 相关Prisma Schema需要清理 
## 二、业务流程影响评估 
### 2.1 核心支付流程（影响度：⭐⭐⭐⭐⭐） **当前流程：** 1. 医生开方 → 创建订单 2. 从诊所预付账户扣款 3. 支付成功 → 订单状态更新为PAID 4. 退款时返还到诊所账户 **影响说明：** - 整个支付模式需要重新设计 - 预付费便利性将丢失 - 财务对账流程需要重构 
### 2.2 事件系统（影响度：⭐⭐⭐） 需要替换的事件： - `account.deducted` - 账户扣款成功 - `account.deduction.failed` - 账户扣款失败 - `account.refunded` - 账户退款成功 
### 2.3 用户体验（影响度：⭐⭐⭐⭐） - 医生每次开方都需要支付操作 - 失去批量预付的便利性 - 财务管理复杂度增加 
## 三、替代方案分析 
### 方案A：直接Stripe支付模式 ```typescript // 改造后的支付流程 async createPaymentForOrder(orderId: string, amount: number) { // 直接创建Stripe PaymentIntent const paymentIntent = await stripe.paymentIntents.create({ amount: amount * 100, currency: 'usd', metadata: { orderId } }); // 返回给前端处理支付 } ``` - **优点**：简化架构，减少维护成本 - **缺点**：用户体验下降，每次都需要支付操作 - **工作量**：2-3天 
### 方案B：个人账户钱包系统 ```typescript // 新的用户级别账户 interface IUserWallet { userId: string; balance: number; // ... 其他字段 } ``` - **优点**：保留预付费模式，更加灵活 - **缺点**：需要全新设计和实现 - **工作量**：1-2周 
### 方案C：混合支付模式 - 支持直接支付和简化版账户支付 - **优点**：平滑过渡，用户可选 - **缺点**：系统复杂度增加 - **工作量**：1周 ## 四、影响量化评估

## 五、建议与结论 
### 5.1 总体评估 取消诊所账户管理模块的影响程度为：**高度影响（7/10）** 
### 5.2 建议 1. **短期方案**：保留诊所账户模块，但简化功能 2. **中期方案**：实施方案C（混合模式），逐步过渡 3. **长期方案**：根据用户反馈决定最终模式 
### 5.3 风险提示 - ⚠️ 已有用户的账户余额需要妥善处理 - ⚠️ 历史交易记录需要保留用于审计 - ⚠️ 需要提前通知用户并提供过渡期 
### 5.4 如果必须取消 最小化影响的实施步骤： 1. 实现直接Stripe支付作为替代（2-3天） 2. 保留历史数据只读访问（1天） 3. 更新所有相关文档和API（1天） 4. 全面测试新支付流程（2天） 5. 制定数据迁移和用户过渡计划（1天） **总工期估算：1-2周**
