# PRD逆向工程技术要素文档 - 业务逻辑要素

## 1. 核心业务模型技术架构

### 1.1 B2B2C平台运营模式技术定义
**业务角色枚举体系**：
- 主体角色：执业医师(practitioner)、药房操作员(pharmacy_operator)、系统管理员(admin)（当前MVP开发阶段不设置患者用户角色，也不在系统中输入或储存患者隐私信息）
- 角色关系：医师-平台-药房的三方协作，患者通过线下处方凭证方式接入
- 权限层级：基于角色的分层访问控制，医师仅访问自有处方，药房仅处理分配订单，唯一管理员账户具备全局数据访问和log管理权限

**三方业务关系建模**：
- 医师业务线：用户身份 → 执业账户 → 处方创建 → 资金扣费 → QR码生成（资金扣费基于医师账户余额；医师通过充值/提现行为控制余额；平台可以通过promo code等形式赠送不可提现的余额给医师账户）
- 药房业务线：扫码接收 → 履约配药 → 上传凭证 → 成本记录 → 结算申请（药房端成本记录体现为上传履约凭证生成仅与该履约药房关联的采购订单PurchaseOrder/PO，PO由履约药品重量和药房自定义价格表形成价格，平台管理员审核PO内容包括表格中的履约凭证，通过后自动将该PO金额转入药房账户余额已备批量提现，即结算申请）
- 平台业务线：差价收益 → 履约审核 → 成本结算 → 资金划转（参考上方药房履约-平台生成PO由管理员审核-通过后转入药房余额-药房提现结算申请这条路线）

### 1.2 价差盈利机制技术原理
**双价格体系架构**：
- 基准价格层：药品基准价格(basePrice)作为医师收费标准
- 履约价格层：药房自定义价格表(PharmacyPriceList)作为成本标准
- 差价控制层：通过价格表审核机制控制履约成本上限

**盈利计算技术逻辑**：
- 收入确认时点：医师账户扣款成功时立即确认平台收入（医师账户充值/余额/赠送余额应该被记录为平台对医师用户的预付款/负债，当医师账户扣款成功时才能确认为平台收入）
- 成本确认时点：药房履约审核通过时确认平台成本（平台对履约后生成的PO对应平台向药房账户的转入金额，这部分应被视为平台对药房的应付账款和平台成本，并且在药房发起批量提现结算申请时进行实际的支付）
- 盈利实现方式：收入与成本的时间差形成现金流管理空间

**资金流控制机制**：
- 预付费托管：医师账户采用余额保障机制（MVP阶段暂不实现信用额度功能）
- 延迟结算：药房成本通过批量提现方式延后支付
- 风险控制：通过审核每SKU药房自定义价格表不得高于药品基准价格表的方式控制价格差来控制成本确认；履约凭证用于明确该张处方最终由哪个药房供货和获取PO

### 1.3 用户角色业务关系技术实现
**医师-平台关系**：
- 账户体系：独立的执业医师账户(PractitionerAccount)管理
- 资金管理：基于余额的账户模式（MVP阶段暂不实现信用额度功能）
- 权限边界：仅能访问自己创建的处方和相关订单

**药房-平台关系**：  
- 接入模式：通过药房账户(PharmacyAccount)接入平台
- 履约模式：扫码接收订单，上传履约凭证，申请批量结算，维护自定义价格表
- 结算控制：通过提现申请(WithdrawalRequest)控制资金划转

**患者-平台关系**：
- 匿名化处理：不存储患者个人信息，仅通过QR码验证身份
- 线下凭证：QR码包含处方验证信息，支持线下核验
- 隐私保护：处方信息与患者身份完全解耦

**管理员-平台关系**：
唯一账户；全局权限；账户申请审批/履约PO审批/提现申请审批

## 2. 核心业务流程技术架构

### 2.1 处方全生命周期技术流程
**第一阶段：处方创建(DRAFT状态)**
- 技术入口：医师通过认证接口创建草稿处方
- 验证逻辑：医师权限验证、药品存在性验证、业务规则验证
- 状态控制：创建时为草稿状态，不影响库存和资金

**第二阶段：处方开具(PAID状态)**  
- 资金扣费：通过事务机制确保账户扣费与处方开具的原子性
- QR码生成：基于处方ID和时间戳生成唯一验证码
- 状态流转：从草稿状态转为已支付状态

**第三阶段：药房履约(PENDING_REVIEW状态)**
- 扫码验证：药房通过QR码从后端数据库中获取处方详情和配药要求
- 履约操作：配药完成后上传履约凭证照片
- 成本记录：系统自动生成采购订单(PurchaseOrder)记录实际成本 

**第四阶段：平台审核(FULFILLED状态)**
- 审核流程：管理员审核PO的真实性和完整性
- 成本确认：审核通过后确认药房履约成本
- 结算准备：根据审核通过的PO金额做系统内转账，标记该PO为FULFILLED，总可提现余额为与该药房关联的PO总金额

**第五阶段：资金结算（PO的SETTLED状态）**
- 批量处理：药房通过批量勾选与该药房关联的PO申请获得结算资金
- 自动化流程：结算完成后自动邮件通知和状态更新
- 审计记录：完整记录资金流转的审计追踪

### 2.2 支付结算技术时序
**实时扣款机制**：
- 事务控制：使用数据库事务确保账户扣费的原子性
- 乐观锁：通过版本控制防止并发扣款导致的数据不一致
- 余额+信用：优先扣除账户余额（MVP阶段暂不实现信用额度功能）

**先扣款后开方原则**：
- 业务逻辑：账户扣费成功后才允许生成QR码和允许保存/导出/打印处方
- 异常处理：扣费失败时自动回滚处方状态到草稿
- 资金安全：防止无资金保障的处方流入履约环节

**延迟结算策略**：
- 成本控制：履约PO审核通过后才确认药房成本
- 批量处理：通过批量提现降低结算成本和提高效率
- 现金流管理：时间差为平台提供资金使用空间

### 2.3 药房履约业务技术规则
**动态价格重算**：
- 履约时基于药房当前价格表重新计算实际成本
- 价格版本控制：保存履约时的价格快照避免历史数据不一致
- 成本上限控制：通过价格表审核机制控制履约成本

**履约凭证技术要求**：
- 必须字段：配药照片和上传时间即构成履约凭证；每个药房仅有唯一的药房账户，可跨平台多设备登录
- 存储机制：通过文件上传服务将履约凭证储存在新生成的PO表格行内
- 审核标准：管理员基于凭证完整性和真实性进行审核

**自动化成本记录**：
- 履约提交时自动生成采购订单记录
- 基于履约数量和药房价格自动计算成本金额
- 成本数据为后续结算和盈利分析提供基础数据

## 3. 业务规则引擎技术架构

### 3.1 处方验证规则体系
**基础数据验证**：
- 帖数范围：1-30帖的业务约束验证
- 药品完整性：药品ID、克重、用药说明的完整性检查
- 数值合理性：克重大于0、金额非负的数值验证

**权限验证机制**：
- 医师资质：验证执业医师资格和有效期
- 处方归属：确保医师只能访问自己创建的处方
- 操作权限：基于用户角色验证业务操作权限

**业务逻辑验证**：
- 状态依赖：验证处方状态是否允许当前操作
- 药品可用性：验证药品是否存在且可用于处方
- 账户状态：验证医师账户状态和可用资金

### 3.2 账户管理业务逻辑
**复合账户算法**：
- 可用资金计算：账户余额（MVP阶段暂不实现信用额度功能）
- 扣费优先级：优先使用账户余额（MVP阶段暂不实现信用额度补充模式）
- 额度管理：基于余额的资金管理模式（MVP阶段暂不实现信用额度分配、使用、还款等功能）

**资金安全控制**：
- 并发控制：通过乐观锁防止并发操作导致的资金不一致
- 事务保障：关键资金操作使用数据库事务确保原子性
- 异常恢复：扣费失败时的自动回滚和异常处理机制

**审计追踪机制**：
- 交易记录：完整记录每笔资金变动的来源和去向
- 版本控制：账户余额变更的版本控制和历史追踪
- 异常监控：资金异常变动的实时监控和告警机制

### 3.3 订单状态流转控制
**状态机技术架构**：
- 状态定义：草稿、已支付、待审核、已履约、已取消、已过期
- 转换规则：定义每个状态允许转换到的目标状态集合
- 验证机制：状态转换前的前置条件验证

**决策点控制逻辑**：
- 支付决策：基于账户余额的支付能力判断（MVP阶段暂不考虑信用额度）
- 履约决策：基于药房能力和价格的履约分配决策
- 审核决策：基于履约凭证质量的审核通过决策

**异常状态处理**：
- 超时机制：草稿状态处方的自动过期处理
- 异常恢复：支付失败、履约异常等的状态回滚机制
- 补偿处理：异常情况下的资金退还和状态修复

## 4. 业务约束技术实现

### 4.1 医疗合规性技术保障
**处方隐私技术架构**：
- 匿名化设计：处方记录不包含患者个人身份信息
- QR码验证：通过加密QR码实现患者身份的间接验证
- 数据最小化：只收集和存储业务必需的最小数据集

**医师资质技术验证**：
- 执业资格：通过执业证书编号和有效期验证医师资质
- 权限边界：基于医师ID的数据访问权限控制
- 审计合规：完整记录医师的处方操作用于合规审查

**药品追溯技术机制**：
- 数据快照：保存开方时的药品信息快照避免历史数据变更
- 版本控制：药品信息的版本管理和变更追踪
- 审计链条：从处方创建到履约完成的完整审计链条

### 4.2 隐私保护技术逻辑
**数据分离架构**：
- 身份分离：用户身份信息与业务数据的物理分离
- 权限隔离：基于角色的数据访问权限隔离
- 存储分离：敏感数据与业务数据的存储分离

**最小化收集原则**：
- 按需收集：只在业务必需时才收集用户数据
- 用途限制：收集的数据仅用于声明的业务用途
- 保存期限：基于业务需要和法律要求的数据保存期限控制

**访问控制技术**：
- 基于角色的访问控制(RBAC)：细粒度的权限控制体系
- 数据脱敏：敏感数据的显示脱敏和传输加密
- 审计日志：完整记录数据访问和操作的审计日志

### 4.3 财务安全技术防护
**并发安全控制**：
- 乐观锁机制：通过版本字段防止并发修改导致的数据不一致
- 事务控制：关键业务操作的事务原子性保障
- 死锁避免：通过合理的锁顺序和超时机制避免死锁

**幂等性技术保护**：
- 幂等键机制：通过幂等键防止重复操作
- 去重逻辑：基于业务特征的操作去重逻辑
- 状态验证：操作前的状态验证防止重复执行

**异常恢复机制**：
- 补偿事务：关键业务操作失败时的自动补偿机制
- 状态修复：异常状态的自动检测和修复机制
- 人工介入：自动恢复失败时的人工介入流程

## 6. 药房价格表审核业务流程技术架构

### 6.1 价格表提交与验证技术流程
**价格表上传业务逻辑**：
- 提交触发：药房操作员通过认证API上传价格表文件(CSV/Excel格式)
- 格式验证：自动验证文件格式、药品SKU有效性、价格数值合理性
- 数据解析：解析价格表结构映射到标准化药品信息字段
- 版本控制：自动生成版本号，保持历史价格表完整追溯

**药品信息一致性技术验证**：
- SKU匹配验证：价格表中药品SKU必须与Medicine主数据完全匹配
- 字段一致性：药品名称、计量单位、分类必须与主数据保持一致
- 数据完整性：验证必填字段completeness和价格精度correctness
- 重复检测：检测同一药品在价格表中的重复定价entries

**basePrice约束技术验证算法**：
- 违规检测：逐行比较药房定价与药品basePrice，识别超出基准价格的drug items
- 风险等级计算：基于违规金额和比例计算风险等级(low/medium/high/critical)
- 告警生成：自动生成价格违规告警详情JSON，包含具体药品SKU、违规金额、风险说明
- 阈值控制：设置可配置的风险阈值触发不同级别的审核要求

### 6.2 管理员审核流程技术实现
**多级审核决策引擎**：
- 自动预审：无违规或低风险价格表可设置自动审批标识
- 人工审核：中高风险价格表强制require人工审核review
- 审核优先级：基于risk level和submission time的审核队列sorting algorithm
- 审核时效：设置审核SLA和超时escalation机制determined by business rules

**审核业务规则引擎**：
- 价格合理性：验证药房定价的market reasonability和competitive benchmarking
- 历史一致性：对比药房历史价格表version consistency和变化合理性
- 供应能力：评估药房对high-volume药品的fulfillment capability
- 合规性检查：确保价格表符合pharmaceutical pricing regulations

**审核决策技术路径**：
- 通过条件：无违规或acceptable risk level，automatic/manual approval
- 拒绝条件：serious violations、unreasonable pricing、compliance issues
- 有条件通过：minor issues需要药房adjustment后重新提交
- 挂起处理：需要additional information或external validation的cases

### 6.3 价格违规告警技术机制
**告警分级技术体系**：
- INFO级别：价格变化通知，无需immediate action
- WARNING级别：价格deviation超出normal range但可接受
- ERROR级别：明显违规需要mandatory review和correction
- CRITICAL级别：严重违规可能impact platform profitability

**告警内容技术结构**：
- 违规药品列表：包含SKU、药品名称、违规金额、违规比例detailed breakdown
- 风险评估：潜在financial impact和business risk analysis
- 建议措施：推荐的correction actions和timeline requirements
- 历史对比：与药房previous submissions和market baseline的comparison

**告警可见性技术控制**：
- 管理员专属：价格违规告警仅管理员可见，确保business intelligence protection
- 药房透明：药房用户完全不可见违规告警detailed information
- 审计记录：完整记录告警生成、处理、解决的audit trail
- 报告生成：定期生成价格违规趋势报告for management review

### 6.4 价格表生效与版本管理技术架构
**生效流程技术控制**：
- 审核通过触发：管理员approval自动触发价格表生效流程
- 生效时间管理：支持immediate生效或scheduled生效日期设置
- 版本切换：新价格表生效时自动disable之前版本ensuring single active version
- 影响范围：新处方订单自动使用最新approved价格表for cost calculation

**版本管理技术策略**：
- 版本号规则：基于timestamp和sequence的unique version identification
- 历史保留：完整保留所有历史版本for audit和data analysis purposes
- 快照机制：每次价格变更保存complete snapshot避免data inconsistency
- 回滚能力：支持紧急情况下的价格表version rollback functionality

**价格表失效技术处理**：
- 自动失效：设置价格表expiry date自动失效过期版本
- 手动失效：管理员可manual disable有问题的价格表版本
- 失效影响：失效价格表不影响已生成的historical orders和PO records
- 通知机制：价格表即将失效时自动notification提醒药房更新

### 6.5 价格表审核异常处理技术机制
**数据质量异常技术处理**：
- 格式错误：不支持格式自动reject并提供format requirements详细说明
- 数据缺失：必填字段missing导致validation failure和specific error messages
- 数据冲突：药品信息不一致触发data reconciliation workflow
- 批量错误：大量错误时提供batch error report便于药房bulk correction

**审核流程异常技术恢复**：
- 审核超时：设置auto-escalation到senior管理员or system administrator
- 审核冲突：多管理员同时审核时的conflict resolution mechanism
- 系统故障：审核过程中system failure的recovery和resume capability
- 状态不一致：审核状态异常时的automatic detection和correction logic

**业务规则异常技术适配**：
- 规则变更：业务规则更新时对pending审核的retroactive application策略
- 特殊情况：需要break standard rules的exceptional case handling workflow
- 紧急审核：urgent price list changes的expedited review process
- 回退处理：审核通过后发现问题的post-approval correction mechanism

## 7. 收益模式技术实现

### 7.1 价格计算技术算法
**多层价格体系**：
- 基准价格层：药品的平台统一基准价格
- 履约价格层：药房自定义的实际履约价格
- 差价控制层：通过审核机制控制价格差异范围

**实时计算机制**：
- 订单总额：基于基准价格和处方数量的实时计算
- 履约成本：基于药房价格和实际履约数量的成本计算
- 盈利分析：收入与成本的实时差额计算和趋势分析

**价格版本控制**：
- 历史价格：保留价格变更历史用于历史订单分析
- 快照机制：订单创建时保存价格快照避免后续价格变更影响
- 版本管理：价格表的版本管理和生效时间控制

### 7.2 收益分配技术逻辑
**收入确认机制**：
- 实时确认：医师支付成功时立即确认平台收入
- 收入记录：详细记录收入来源、金额、时间等信息
- 收入分类：按业务类型、药品类别等维度对收入进行分类

**成本延迟结算**：
- 成本确认：履约PO审核通过后确认实际履约成本
- 延迟支付：通过批量结算降低成本和提高效率
- 成本控制：通过审核机制控制异常成本

**现金流管理**：
- 时间差利用：收入与成本确认的时间差形成资金使用空间
- 流动性管理：基于历史数据预测资金需求和流动性
- 风险控制：设置资金池下限确保结算资金充足

### 7.3 结算周期技术控制
**批量结算机制**：
- 申请流程：药房通过批量提现申请获得结算资金
- 审批流程：管理员审核提现申请的合理性和真实性
- 自动化程度：审核通过后的自动转账和状态更新

**结算周期管理**：
- 周期设置：基于业务需要和现金流情况设置结算周期
- 灵活调整：根据业务量和资金状况灵活调整结算频率
- 异常处理：结算异常情况的处理流程和补救机制

**结算监控体系**：
- 实时监控：结算申请、审核、执行的实时状态监控
- 异常告警：结算异常情况的自动告警和处理
- 数据分析：结算数据的统计分析和趋势预测
