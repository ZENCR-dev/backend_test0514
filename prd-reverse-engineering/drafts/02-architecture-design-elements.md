# PRD逆向工程技术要素文档 - 架构设计要素

## 1. 分层架构设计技术实现

### 1.1 MVP简化DDD架构模式
**MVP领域边界划分**：
- 认证领域(Auth Domain)：用户身份管理、JWT令牌、角色验证
- 处方领域(Prescription Domain)：处方管理、平台药品表、医师账户、充值支付
- 药房领域(Pharmacy Domain)：药房自定义价格表、履约管理、PO生成、提现Invoice
- 系统领域(System Domain)：API日志、配置管理、管理员超级权限

**MVP聚合根设计**：
- 用户聚合：User作为聚合根，简化角色管理（医师、药房操作员、管理员）
- 处方聚合：Prescription作为聚合根，管理PrescriptionMedicine、PurchaseOrder关联
- 账户聚合：PractitionerAccount和PharmacyAccount独立管理各自资金流

**MVP依赖关系控制**：
- Service层直接调用Prisma Client，移除Repository抽象层（MVP阶段简化设计，移除过度抽象）
- 跨领域通信通过NestJS EventEmitter实现，保持完整的业务事件通知
- 依赖注入容器管理服务生命周期和配置

### 1.2 MVP简化分层架构（3层）
**API控制层(Controller Layer)**：
- 职责边界：HTTP请求处理、参数验证、JWT权限检查、响应格式化
- 技术实现：NestJS装饰器系统(@Controller、@Get、@Post、@UseGuards)
- 依赖注入：通过构造函数注入Service层依赖
- 异常处理：统一异常过滤器处理业务异常和HTTP状态码映射

**业务逻辑层(Service Layer)**：
- 职责边界：业务规则实现、流程编排、Prisma事务控制、事件发布
- 技术实现：@Injectable装饰器标记、直接注入其他Service和Prisma Client
- 数据访问：直接使用Prisma Client进行类型安全的数据库操作
- 事务管理：使用Prisma事务API确保业务操作的原子性
- 错误传播：业务异常包装和上下文信息保留

**数据访问层(Prisma Layer)**：
- Prisma Client提供类型安全的查询接口和事务支持
- 自动处理连接池管理和查询优化
- 内置迁移管理和Schema演进支持

**MVP横切关注点处理**：
- 中间件(Middleware)：API调用日志记录、基础性能记录
- 守卫(Guards)：JWT认证验证、角色权限检查
- 过滤器(Filters)：全局异常处理、用户友好错误响应

### 1.3 MVP模块架构（3+1结构）
**模块依赖图**：
```
AppModule (根模块)
├── AuthModule (用户认证+角色管理)
├── PrescriptionModule (处方+平台药品表+医师账户+充值支付)
├── PharmacyModule (药房+自定义价格表+履约+PO+提现Invoice)
└── CommonModule (API日志+配置+管理员超级权限)
```

**MVP模块职责**：
- **AuthModule**：JWT认证、用户管理、角色验证（医师、药房操作员、管理员）
- **PrescriptionModule**：处方全生命周期、医师账户余额管理、充值支付集成
- **PharmacyModule**：药房履约、价格表管理、PO处理、Invoice生成邮件发送
- **CommonModule**：系统配置、API日志记录、管理员权限控制

## 2. MVP设计模式应用

### 2.1 依赖注入(DI)容器核心配置
**服务注册机制**：
- Provider类型：主要使用Class providers和Factory providers（配置类）
- 作用域控制：DEFAULT(单例)为主，REQUEST(请求级)用于特殊场景
- 配置管理：ConfigService统一管理环境配置、数据库连接配置

**注入策略**：
- 构造函数注入：所有服务依赖通过构造函数注入
- 配置注入：通过ConfigService注入数据库连接、JWT密钥等配置
- Service层直接注入Prisma Client，无需Repository抽象

### 2.2 事件驱动模式（简化版）
**事件系统架构**：
- 事件定义：强类型事件接口，明确的事件负载结构
- 发布机制：使用NestJS EventEmitter2进行同步事件发布
- 订阅机制：@OnEvent装饰器实现事件监听

**核心业务事件**：
- 支付成功/失败事件：触发处方状态更新
- 履约完成事件：触发PO生成和药房账户余额更新
- PO审核通过/拒绝事件：控制资金流转
- 提现申请处理事件：Invoice生成和邮件发送

### 2.3 MVP移除的复杂模式
**不适用于MVP的设计模式**：
- Repository模式：Prisma Client已提供足够抽象，无需额外封装
- 策略模式：MVP阶段支付方式单一（余额扣费），无需策略选择
- 工厂模式：服务创建通过DI容器管理，无需复杂工厂
- 复杂缓存策略：MVP用户量小，Prisma内置优化已足够

## 3. MVP模块化架构

### 3.1 简化模块系统
**模块类型**：
- 根模块(AppModule)：应用程序入口、全局配置、模块导入
- 功能模块(3个)：AuthModule、PrescriptionModule、PharmacyModule
- 通用模块(CommonModule)：共享服务、API日志、配置管理

**模块依赖管理**：
- 导入(imports)：明确的模块间依赖声明
- 导出(exports)：必要服务的对外暴露
- 提供者(providers)：模块内服务注册
- 控制器(controllers)：HTTP端点注册

### 3.2 MVP模块通信
**服务注入通信**：
- 跨模块服务依赖注入（如PrescriptionService注入到PharmacyModule）
- DTO标准化数据传输
- 统一响应格式

**事件驱动通信**：
- 关键业务事件的跨模块通知
- 解耦的发布订阅模式
- 事件处理失败的优雅降级

### 3.3 模块生命周期（简化）
**初始化阶段**：
- OnModuleInit：模块初始化钩子、基础资源准备
- 数据库连接检查、配置验证

**销毁阶段**：
- OnModuleDestroy：资源清理、连接关闭
- 优雅关闭处理

## 4. MVP事件驱动架构

### 4.1 简化事件系统设计
**业务事件定义**：
- 事件命名：动词过去式命名（PaymentSucceeded、FulfillmentCompleted）
- 事件负载：关键业务数据、时间戳、关联ID
- 事件边界：关键业务状态变更事件

**核心事件类型**：
- 支付相关：PaymentSucceeded、PaymentFailed、AccountRecharged
- 处方相关：PrescriptionCreated、PrescriptionPaid、PrescriptionFulfilled
- 履约相关：FulfillmentCompleted、PurchaseOrderApproved、WithdrawalRequested

### 4.2 MVP事件发布订阅
**事件发布机制**：
- 同步发布：使用NestJS EventEmitter2的同步事件发布
- 事务一致性：事件发布与数据库操作在同一事务中

**事件订阅机制**：
- 装饰器订阅：@OnEvent装饰器实现编译时订阅
- 错误隔离：单个事件处理器失败不影响其他处理器
- 简单重试：基础的错误重试机制

### 4.3 MVP移除的复杂事件机制
**不适用于MVP的事件特性**：
- 事件持久化：无需事件存储和重放
- 分布式事件总线：单体应用内事件通信已足够
- 复杂重试机制：基础重试足以应对MVP场景
- 事件版本控制：MVP阶段事件结构相对稳定

## 5. MVP性能控制策略

### 5.1 基础数据库管理
**Prisma连接管理**：
- 连接池：使用Prisma内置连接池，默认配置适用于MVP规模
- 事务管理：使用Prisma事务API确保数据一致性
- 查询优化：利用Prisma类型安全查询和内置优化

**MVP事务策略**：
- 事务边界：关键业务操作（支付、履约）使用事务保证
- 简单事务：避免复杂的嵌套事务，保持事务简洁
- 错误处理：事务失败时的清晰错误处理和回滚

### 5.2 MVP移除的复杂性能机制
**不适用于MVP的性能策略**：
- 乐观锁/悲观锁：MVP并发量低，Prisma事务已足够
- 多级缓存系统：100用户规模无需复杂缓存
- 连接池调优：Prisma默认配置适用于MVP
- 分布式事务：单体应用无需分布式事务协调
- 性能监控体系：基础日志记录足够定位问题

## 6. 统一错误处理机制技术架构

### 6.1 分层错误处理体系设计
**全局异常过滤器架构**：
- NestJS ExceptionFilter统一捕获所有未处理异常
- 多层级异常分类：业务异常、系统异常、第三方服务异常
- HTTP状态码智能映射：基于异常类型自动选择合适的HTTP状态码
- 上下文信息保留：异常传播过程中保持完整的业务上下文

**异常分类技术体系**：
- BusinessException：业务规则违反异常(400 Bad Request)
- ValidationException：数据验证失败异常(422 Unprocessable Entity)  
- AuthenticationException：认证失败异常(401 Unauthorized)
- AuthorizationException：权限不足异常(403 Forbidden)
- ResourceNotFoundException：资源不存在异常(404 Not Found)
- ConflictException：资源冲突异常(409 Conflict)
- SystemException：系统内部错误异常(500 Internal Server Error)

**错误代码标准化机制**：
- 模块化错误代码：AUTH_001、PRESCRIPTION_002、PHARMACY_003
- 层级化错误分类：业务类别.具体错误.子错误码
- 国际化错误消息：支持中英文错误信息切换
- 客户端友好格式：统一的错误响应JSON结构

### 6.2 业务异常处理技术实现
**医师业务异常处理**：
- InsufficientBalanceException：账户余额不足异常
- PrescriptionValidationException：处方验证失败异常
- InvalidMedicineException：无效药品异常
- AccountSuspendedException：账户被暂停异常
- DuplicatePrescriptionException：重复处方异常

**药房业务异常处理**：
- PriceListValidationException：价格表验证失败异常
- BasePriceViolationException：基准价格违规异常
- FulfillmentProofException：履约凭证异常
- PharmacyAccessDeniedException：药房访问拒绝异常
- PriceListConflictException：价格表冲突异常

**支付业务异常处理**：
- PaymentProcessingException：支付处理异常
- PaymentTimeoutException：支付超时异常
- RefundException：退款异常
- TransactionLockException：交易锁定异常
- PaymentValidationException：支付验证异常

### 6.3 异常传播与包装技术机制
**Service层异常包装策略**：
- 原始异常包装：保留底层异常信息用于调试
- 业务上下文添加：添加用户ID、处方ID等业务关键信息
- 异常链追踪：维护完整的异常调用链
- 敏感信息过滤：移除可能暴露系统内部结构的敏感信息

**Controller层异常处理**：
- @UseFilters装饰器统一异常处理
- 异常响应格式标准化：{error_code, message, details, timestamp}
- 请求ID关联：每个错误响应包含唯一请求追踪ID
- 客户端适配：基于Accept header提供不同格式错误响应

**Prisma异常转换机制**：
- P2002(唯一约束违反) → ConflictException
- P2025(记录不存在) → ResourceNotFoundException  
- P2003(外键约束违反) → ValidationException
- 连接异常 → SystemException
- 查询超时 → TimeoutException

### 6.4 错误日志与监控技术体系
**结构化错误日志**：
- 错误级别分类：ERROR、WARN、INFO、DEBUG
- 统一日志格式：timestamp、level、error_code、message、context、stack_trace
- 关键字段索引：user_id、prescription_id、pharmacy_id、error_code
- 日志聚合：按错误类型、模块、时间维度聚合分析

**错误监控告警机制**：
- 错误率阈值监控：API错误率超过5%触发告警
- 关键业务异常：支付失败、处方异常立即告警
- 系统异常监控：数据库连接失败、服务不可用告警
- 异常趋势分析：错误增长趋势监控和预警

**错误分析与报告**：
- 错误统计仪表板：实时错误数量、类型、分布统计
- 错误影响分析：错误对业务流程的影响评估
- 根因分析：常见错误的根本原因分析和解决方案
- 错误报告：定期生成错误分析报告供技术团队优化

### 6.5 客户端错误处理技术标准
**统一错误响应格式**：
```json
{
  "success": false,
  "error": {
    "code": "PRESCRIPTION_001",
    "message": "处方药品验证失败",
    "details": "药品 SKU-001 不在可用药品列表中",
    "field": "medicine_id",
    "timestamp": "2024-01-01T10:00:00Z",
    "request_id": "req_123456"
  }
}
```

**HTTP状态码映射标准**：
- 200：成功响应
- 400：客户端请求错误(BusinessException、ValidationException)
- 401：认证失败(AuthenticationException)
- 403：权限不足(AuthorizationException)  
- 404：资源不存在(ResourceNotFoundException)
- 409：资源冲突(ConflictException)
- 422：数据验证失败(ValidationException)
- 500：服务器内部错误(SystemException)

**错误重试与降级策略**：
- 重试机制：临时性错误自动重试，指数退避策略
- 熔断机制：连续失败达到阈值时暂停服务调用
- 降级处理：关键服务不可用时提供备用服务
- 用户友好提示：技术错误转换为用户可理解的提示信息

### 6.6 异常恢复与补偿技术机制
**事务异常恢复**：
- 自动回滚：Prisma事务失败时自动回滚数据变更
- 补偿事务：关键业务操作失败后的自动补偿机制
- 状态修复：数据不一致时的自动检测和修复
- 人工介入：自动恢复失败时的人工干预流程

**业务流程异常处理**：
- 支付异常：支付失败时处方状态回滚、资金解冻
- 履约异常：履约失败时PO状态重置、资金释放
- 审核异常：审核超时时自动escalation或状态重置
- 数据同步异常：关键数据不一致时的同步修复机制

**系统异常应急响应**：
- 服务降级：非关键功能暂停，保障核心业务正常
- 数据备份：异常发生时自动触发数据备份
- 故障隔离：问题服务隔离，防止异常传播
- 快速恢复：预定义恢复脚本，快速恢复服务正常

## 8. 容器化vs传统部署策略影响分析

### 8.1 容器化部署技术架构研究
**Docker容器化技术实现方案**：
- NestJS应用容器化：Node.js 18 Alpine基础镜像、多阶段构建优化镜像大小
- PostgreSQL数据库容器：官方postgres:14-alpine镜像、数据卷持久化存储
- Nginx反向代理：静态文件服务、SSL终止、负载均衡配置
- Docker Compose编排：开发环境一键启动、服务依赖管理、环境变量配置

**容器化架构技术优势**：
- 环境一致性：开发、测试、生产环境完全一致，消除"在我机器上可以运行"问题
- 快速部署：镜像构建一次，多环境复用，部署时间从小时级降低到分钟级
- 资源隔离：CPU、内存、网络隔离，应用间不相互影响，提升系统稳定性
- 水平扩展：通过Docker Swarm或Kubernetes实现自动化水平扩展

**容器化技术实现细节**：
- 多阶段构建：build阶段编译TypeScript、production阶段仅包含运行时文件
- 健康检查：/health端点健康检查、容器自动重启机制
- 日志管理：stdout/stderr日志收集、集中化日志管理和分析
- 安全强化：非root用户运行、最小权限原则、定期安全扫描

### 8.2 传统部署策略技术分析
**传统服务器部署技术实现**：
- 专用服务器：物理服务器或VPS直接部署Node.js应用
- 系统级依赖：Node.js运行时、PostgreSQL数据库、Nginx反向代理系统级安装
- 进程管理：PM2进程管理器、自动重启、集群模式、日志轮转
- 系统服务：systemd服务管理、开机自启动、服务监控

**传统部署技术优势**：
- 简单直接：无需学习容器技术，传统运维团队容易理解和维护
- 性能开销：无容器层性能开销，直接使用宿主机资源
- 调试便利：直接访问文件系统、进程、日志，调试和故障排查相对简单
- 成本可控：无需容器编排平台，基础设施成本相对较低

**传统部署技术挑战**：
- 环境依赖：不同环境配置差异，依赖版本冲突，环境配置复杂
- 部署复杂：手动部署步骤多，容易出错，回滚困难
- 扩展性差：水平扩展需要大量手动工作，自动化程度低
- 运维负担：系统更新、安全补丁、依赖管理工作量大

### 8.3 MVP阶段部署策略影响分析
**开发效率影响对比**：
- 容器化：Docker环境搭建增加初期学习成本，但后续开发环境一致性显著提升开发效率
- 传统部署：开发环境搭建简单，但不同开发者环境差异导致频繁的环境问题
- 本地开发：容器化docker-compose一键启动vs传统手动安装配置数据库、服务
- 新人上手：容器化新人环境搭建时间从天级降低到小时级

**运维成本影响评估**：
- 人力成本：容器化需要学习Docker/K8s技术，传统部署依赖现有运维技能
- 时间成本：容器化初期搭建时间较长，但后续部署、扩展、维护时间显著减少
- 故障恢复：容器化自动重启、快速回滚，传统部署需要手动操作和故障定位
- 安全维护：容器化基础镜像统一更新，传统部署每台服务器单独维护

**技术债务累积分析**：
- 容器化：初期投入高，但技术债务累积慢，未来扩展和维护成本低
- 传统部署：初期投入低，但随着规模增长技术债务快速累积，后期重构成本高
- 迁移成本：传统→容器化迁移复杂度中等，容器化→传统迁移难度大
- 技能依赖：容器化需要专业技能，传统部署通用技能需求

### 8.4 业务影响与风险评估
**可用性影响技术对比**：
- 容器化：自动健康检查、故障自愈、滚动更新，可用性提升显著
- 传统部署：依赖手动监控、人工恢复，故障恢复时间长
- 灾难恢复：容器化镜像备份简单，传统部署需要完整系统备份
- 数据安全：两种方案数据库备份策略相似，但容器化配置管理更规范

**性能影响技术测试**：
- CPU开销：容器化增加3-5%CPU开销，对MVP规模业务影响可忽略
- 内存开销：容器化增加50-100MB内存开销，在现代服务器配置下可接受
- 网络延迟：容器网络增加<1ms延迟，对API响应时间影响微小
- I/O性能：使用绑定挂载数据卷，数据库I/O性能与传统部署相当

**扩展性影响评估**：
- 水平扩展：容器化支持自动扩展，传统部署需要大量手动工作
- 负载均衡：容器化天然支持服务发现，传统部署需要手动配置
- 微服务演进：容器化为未来微服务架构提供基础，传统部署迁移成本高
- 多环境管理：容器化环境一致性优势在多环境部署中显著体现

### 8.5 成本效益技术分析
**初期投入成本对比**：
- 学习成本：容器化需要1-2周Docker学习时间，传统部署无额外学习成本
- 搭建成本：容器化环境搭建需要2-3天，传统部署1天完成
- 工具成本：容器化可使用免费Docker工具，传统部署可能需要商业监控软件
- 基础设施：两种方案基础硬件需求相似，容器化可能需要略高配置

**长期运营成本分析**：
- 人力成本：容器化运维效率提升30-50%，长期人力成本降低
- 故障成本：容器化故障恢复时间减少70%，业务中断损失显著降低
- 扩展成本：容器化水平扩展成本降低80%，传统部署扩展成本线性增长
- 维护成本：容器化统一维护，传统部署服务器数量增长维护成本快速上升

**ROI时间线技术评估**：
- 短期(3个月)：传统部署投入产出比更高，容器化仍在投入期
- 中期(6-12个月)：容器化开始显现优势，运维效率提升带来成本节约
- 长期(12个月+)：容器化ROI显著高于传统部署，技术债务差异明显
- 拐点分析：通常在6-8个月时容器化累积收益超过传统部署

### 8.6 MVP推荐部署策略
**MVP阶段最优策略技术建议**：
- 推荐方案：容器化部署，使用Docker Compose进行服务编排
- 技术栈：Docker + Docker Compose + PostgreSQL容器 + Nginx容器
- 部署环境：开发、测试、生产环境统一使用容器化部署
- 监控方案：Docker原生监控 + 应用层监控，避免过度复杂化

**实施路径技术规划**：
- 第一阶段(Week 1-2)：开发环境容器化，团队Docker技能培训
- 第二阶段(Week 3-4)：测试环境容器化，CI/CD管道集成Docker
- 第三阶段(Week 5-6)：生产环境容器化，监控告警系统完善
- 后续优化：根据业务增长考虑Kubernetes迁移

**风险缓解技术措施**：
- 技能风险：提前进行Docker培训，准备传统部署回退方案
- 性能风险：生产环境性能测试，确保容器化性能满足业务需求
- 稳定性风险：分阶段迁移，保持传统部署环境作为应急备份
- 运维风险：完善容器化运维文档，建立故障处理标准流程

**决策矩阵技术框架**：
- 如果团队Docker经验丰富：强烈推荐容器化
- 如果追求快速上线：可考虑传统部署，但需规划后续容器化迁移
- 如果预期快速增长：必须选择容器化，传统部署扩展成本过高
- 如果资源极度有限：传统部署初期投入更小，但需考虑技术债务

- ConfigService：统一配置管理，支持动态配置加载
- 配置验证：启动时验证必需配置项

### 9.3 MVP监控告警体系技术架构
**系统健康监控技术实现**：
- 应用健康检查：/health端点检查数据库连接、关键服务状态
- 资源监控：CPU使用率、内存占用、磁盘空间实时监控
- 数据库监控：Prisma连接池状态、查询性能、慢查询识别
- API可用性：关键端点的持续可用性检查和响应时间监控

**业务指标监控技术机制**：
- 处方业务指标：处方创建成功率、支付成功率、履约完成率
- 药房业务指标：价格表审核通过率、履约响应时间、PO处理效率
- 财务业务指标：日交易量、平台收益、结算处理时间、异常交易检测
- 用户活跃度：日活用户数、功能使用频率、用户行为模式分析

**告警分级技术体系**：
- CRITICAL：系统无法提供服务(数据库连接失败、应用crash)
- HIGH：核心业务功能异常(支付失败率>10%、处方创建失败)
- MEDIUM：性能指标异常(API响应时间>2s、错误率>5%)
- LOW：资源使用提醒(磁盘空间<20%、内存使用>80%)

**实时告警通知机制**：
- 邮件告警：CRITICAL和HIGH级别告警立即发送邮件通知
- 短信告警：CRITICAL级别故障触发短信紧急通知
- 钉钉/Slack：业务异常和性能问题webhook推送
- API日志：所有告警事件记录到ApiCallLog表用于分析

**监控数据采集技术架构**：
- 应用层监控：NestJS内置metrics收集、自定义业务指标上报
- 中间件监控：HTTP请求响应时间、错误率、并发数统计
- 数据库监控：Prisma查询性能监控、连接池使用情况
- 系统层监控：通过process.cpuUsage()、process.memoryUsage()收集系统指标

**告警规则引擎技术实现**：  
- 阈值规则：基于固定阈值的简单告警(错误率>5%、响应时间>2s)
- 趋势规则：基于历史数据的异常趋势检测(错误率增长>50%)
- 业务规则：基于业务逻辑的复合告警(支付失败且余额充足)
- 智能降噪：相似告警合并、告警频次控制、维护窗口告警屏蔽

**监控数据存储与分析**：
- 时序数据：API调用量、响应时间等时序指标存储优化
- 聚合统计：按小时/天/周维度聚合业务和系统指标
- 历史分析：保留3个月详细监控数据，1年聚合数据
- 性能基线：建立正常业务模式的性能基线用于异常检测

**监控仪表板技术设计**：
- 实时大屏：关键业务指标、系统状态的实时展示
- 业务仪表板：处方量、交易额、用户活跃度等业务指标
- 技术仪表板：API性能、错误率、系统资源使用情况
- 告警中心：当前告警状态、历史告警趋势、处理状态跟踪

### 9.4 MVP暂时移除的扩展性机制
**未来需要时再引入**：
- API版本管理：MVP阶段API相对稳定
- 复杂配置中心：环境变量配置已足够
- 分布式追踪：单体应用无需复杂追踪
- 微服务治理：当前不需要服务发现、熔断等机制

## MVP架构设计技术要素总结

### MVP核心设计原则
1. **简单优先**：架构复杂度与业务规模匹配，避免过度设计
2. **业务驱动**：技术选型服务于业务验证需求
3. **快速迭代**：支持快速开发和部署的技术栈
4. **扩展预留**：为未来规模化扩展保留架构演进空间
5. **成本控制**：开发和运维成本与MVP阶段资源匹配

### MVP架构质量属性
1. **开发效率**：简化的架构层次，降低开发复杂度
2. **可维护性**：清晰的模块边界，标准化的代码结构
3. **业务适配性**：架构设计紧密贴合业务流程需求
4. **技术债务控制**：合理的简化程度，避免过度技术债务
5. **演进能力**：为规模扩张预留的架构升级路径

### MVP技术决策合理性
1. **NestJS + TypeScript**：成熟稳定的企业级开发框架
2. **Prisma ORM**：现代化数据访问层，类型安全且性能良好
3. **3层架构**：移除Repository层，简化开发和维护成本
4. **简化事件系统**：保持完整业务通知，移除复杂持久化机制
5. **基础监控**：API日志记录足以支持MVP阶段的问题定位

### 从企业级向MVP简化的关键决策

**简化效果对比**：
- 数据库表：从15-20张简化到精确10张
- 架构层次：从4层简化到3层
- 模块数量：从9个复杂模块简化到4个清晰模块
- 设计模式：移除Repository、策略、工厂等复杂模式
- 性能机制：移除乐观锁、多级缓存、复杂监控等

**保留的核心能力**：
- 完整的业务事件通知机制
- Prisma事务保证的数据一致性
- 清晰的模块边界和职责分离
- 基础的API日志和错误追踪
- 为未来扩展预留的架构演进能力

**技术债务控制策略**：
- 避免过早优化，专注业务价值验证
- 保持代码质量和测试覆盖率
- 为规模扩张时的架构升级做好准备
- 通过事件驱动模式为分布式架构演进打基础
